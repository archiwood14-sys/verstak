# Исследование: проектное пространство и документы для АРХИВУД

Дата: 03.11.2026. Задача: команда из 3–5 человек, 3–10 проектов одновременно. Нужно всегда видеть только актуальное, получать историю версий по запросу, искать текстом и голосом, а ИИ-агент должен собирать документы из существующих.

---

## 1. Как это решают профессиональные системы (стройка и проектирование)

### 1.1 ISO 19650 / CDE (Common Data Environment)
- **4 состояния информации:** WIP (в работе, видит только автор) → Shared (передано на согласование или координацию) → Published (утверждено для использования, например «в производство») → Archived (журнал всех переходов и смен статусов, ничего не удаляется). WIP, Shared и Published унаследованы из BS 1192, а Archived ведёт журнал всех «ворот» между состояниями. [UK BIM Framework, Guidance Part C](https://www.ukbimframework.org/wp-content/uploads/2021/02/Guidance-Part-C_Facilitating-the-common-data-environment-workflow-and-technical-solutions_Edition-1.pdf), [DEVB HK, терминология ISO 19650](https://www.devb.gov.hk/filemanager/en/content_1287/Appendix%20I - ISO 19650 Terminologies (v2).pdf)
- **Коды пригодности (suitability) по UK National Annex (табл. NA.1)**, в упрощённом виде: S0 — в работе, S1 — для координации, S2 — для информации, S3 — для ревью и комментариев, S4 — на утверждение; A1…An — утверждено для этапа; B — утверждено с замечаниями. Точная таблица есть в ISO 19650-2 NA. Маппинги в вендорских гайдах расходятся.
- **Ревизии:** P01, P02… для предварительных (Shared), C01, C02… для «контрактных» и утверждённых (Published). Пример: [Pentagon Docs, WIP workflow](https://help.pentagonsolutions.com/PentagonDocsAssistant/General/CDEWIPWorkflow.html). Внутри WIP допустимы подверсии вида P01.1.
- **Что взять маленькой мастерской:** не всю ISO, а три идеи. (1) Документ — это «контейнер» с постоянным кодом и сменяющимися ревизиями, а не набор файлов. (2) Статус пригодности записан в метаданных, а не в имени файла. (3) Переход между статусами — это событие с автором и датой, и оно попадает в журнал.

### 1.2 Procore
- **Drawings:** экран «Current Drawings» показывает только актуальные листы (номер, название, ревизия, дата, статус). При загрузке листа с уже существующим номером он автоматически становится следующей ревизией. Старые ревизии доступны в отчёте «All Sets and Revisions». Можно наложить прошлую ревизию на текущую (overlay) и увидеть, что добавлено и что удалено. [Procore: view drawings](https://support.procore.com/products/online/user-guide/project-level/drawings/tutorials/view-drawings), [upload revisions](https://support.procore.com/products/online/user-guide/project-level/drawings/tutorials/upload-drawing-revisions), [All sets & revisions](https://support.procore.com/products/online/user-guide/project-level/drawings/tutorials/view-the-all-sets-and-revisions-report-in-the-drawings-tool)
- **Submittals и «Ball in Court»:** у каждого согласования виден человек, «у которого мяч», то есть тот, кто сейчас должен действовать. Ответ «Revise and Resubmit» возвращает мяч менеджеру, а тот закрывает текущую ревизию и создаёт новую. [Procore: change ball in court](https://support.procore.com/products/online/user-guide/project-level/submittals/tutorials/change-the-ball-in-court-on-a-submittal), [Workflow best practices](https://v2.support.procore.com/en-ca/process-guides/best-practices-submittals/workflow-management)
- **Как выбирается «последняя» версия в Document Management:** [Procore FAQ](https://v2.support.procore.com/fr-ca/faq-how-does-procore-decide-which-document-version-is-the-latest-in-the-document-management-tool)

### 1.3 Autodesk Construction Cloud (Autodesk Docs)
- Файл с тем же именем, загруженный в ту же папку, становится новой версией. Бейдж «V3» открывает историю версий. Любую старую версию можно сделать актуальной кнопкой «Make Latest»: копия ложится поверх, и ничего не теряется. Для чертежей есть сравнение двух версий наложением или «бок о бок». [Autodesk: View Version History](https://help.autodesk.com/cloudhelp/ENU/Docs-Files/files/file-folder-actions/View_Version_History_Docs.html)

### 1.4 Oracle Aconex
- Обновление документа здесь называется **supersede** («заменить»). Все версии хранятся, удаления нет. Документ можно пометить «больше не используется»: он уходит из реестра, но остаётся в истории. [Aconex: version control & audit trail](https://help.aconex.com/high-compliance-environments/essentials/hce-how-do-version-control-and-the-aconex-audit-trail-work), [Update (Supersede)](https://help.aconex.com/documents/update-document/), [No longer in use](https://help.aconex.com/high-compliance-environments/documents/hce-mark-document-as-no-longer-in-use)
- **Supersede candidate:** если загрузка совпадает по номеру документа и у неё выше ревизия, система сама предлагает заменить старую версию. Так закрываются дубли. [Aconex: supersede candidate](https://help.aconex.com/documents/what-is-a-supersede-candidate/), [Duplicate versions](https://help.aconex.com/documents/duplicate-versions-of-the-same-document/)
- **Event Log + transmittals:** по каждому документу видно, кто и когда его изменил и кому он отправлен.

### 1.5 Bluebeam Revu
- **Compare Documents** обводит облаками различия между двумя PDF и работает даже со сканами. **Overlay Pages** накладывает версии цветными слоями, и их может быть больше двух. [Bluebeam: Compare vs Overlay](https://support.bluebeam.com/revu/features/compare-documents-vs-overlay-pages.html)
- Для АРХИВУД это главный паттерн при сравнении чертежей конструктора: «было / стало» с подсветкой изменений.

### 1.6 PlanRadar
- Документы и планы доступны в мобильном приложении офлайн. Есть версии документов, запросы на согласование файлов и ревью с телефона. Новые планы сразу видны всем участникам. [PlanRadar Help: Webapp & Mobile](https://help.planradar.com/hc/en-gb/articles/22539675406365-PlanRadar-Webapp-Mobile-App-Overview)
- Основная сила PlanRadar — пины-замечания на плане с фото с объекта. Это прямой аналог «фото с объекта, привязанных к месту».

### 1.7 Регистр, transmittal, RFI, submittal: что это и что из этого нужно мастерской
| Понятие | Суть | Аналог в АРХИВУД | Брать? |
|---|---|---|---|
| Document register | Таблица всех документов проекта: код, название, текущая ревизия, статус, дата | «Реестр документов проекта» | **Да, это ядро** |
| Transmittal | Сопроводительное письмо: что, кому, какой ревизии отправлено | Запись «Отправлено заказчику / дизайнеру: КП rev.3, PDF» | Да, как автособытие в ленте |
| RFI | Формальный вопрос по неясности в проекте | «Вопрос дизайнеру / заказчику» с ответом и сроком | Да, в облегчённом виде |
| Submittal | Пакет на утверждение (чертежи, образцы) с ответом «утверждено / с замечаниями / переделать» | «Согласование чертежей / образцов шпона» | **Да, это ключевая боль** |
| Ball in Court | Кто сейчас должен действовать | «Ждём: заказчика / Мансура / Юлию» | **Да** |

Различия между RFI, submittal и transmittal: [ConstructionOnline](https://help.constructiononline.com/en/when-should-i-use-an-rfi-versus-a-submittal-or-a-transmittal), [Datagrid/Procore: transmittal vs submittal](https://datagrid.com/guides/transmittal-vs-submittal-construction), [Fieldwire](https://fieldwire.com/blog/rfis-submittals-specs). Важное предупреждение оттуда: если отправка (transmittal) не попала в журнал согласований, «часы согласования не пошли», и ответа никто не ждёт.

**Не брать:** сложные матрицы прав, многоступенчатые workflow, BIM-модели, тендерные модули, формальные коды ISO в именах файлов.

## 3. UI-паттерны проектного пространства

1. **Список проектов (портфель):** карточки с этапом, «у кого мяч», ближайшим дедлайном и красным флагом «ждём ответа N дней».
2. **Карточка проекта:** шапка (заказчик, дизайнер, адрес, этап, сумма), ниже вкладки «Обзор · Документы · Согласования · Фото · Лента · Вопросы».
3. **Канбан этапов:** колонки «Заявка → Замер → КП/смета → Договор → Конструкторка → Согласование чертежей → Производство → Монтаж → Сдача / гарантия». Карточка проекта перемещается между колонками.
4. **Реестр документов** (паттерн из Procore «Current Drawings», InEight и Newforma): по умолчанию показывается **только последняя ревизия** каждого документа. Фильтр «Последние / Заменённые / Все». Бейдж ревизии (`C02`, `P03`) кликабелен и открывает историю. [InEight: superseded revisions](https://learn.ineight.com/document/content/Document/Document_Control/Uploading_Superseded_Document.htm), [Newforma: document control](https://projectcenter.help.newforma.com/learning/reference-guides/document_control_quick_reference_guide/)
5. **Статус-пилюля** с цветом: Черновик · На согласовании · Утверждено · В производство · Заменён (серый, зачёркнутый, с водяным знаком «ЗАМЕНЁН» при открытии).
6. **Предупреждение при загрузке** (паттерн InEight и Aconex): «Похоже, это новая версия документа "Чертёж кухни" (сейчас C02). Сделать C03?», с вариантами «Да / Это отдельный документ».
7. **Сравнение версий:** для PDF и чертежей — overlay с двумя цветами или «шторка» (паттерн Bluebeam и ACC). Для текста договора или сметы — diff по абзацам или строкам: «добавлено» зелёным, «удалено» красным. Для сметы — разница сумм.
8. **Лента событий проекта** (activity feed): «Юлия загрузила Смету rev.4», «Заказчик утвердил Чертежи C02 (в Telegram)», «Мансур добавил 6 фото с объекта». Каждое событие кликабельно.
9. **Глобальный поиск и «Спросить»:** строка поиска с микрофоном. Ищет по названию, содержимому (OCR и текст PDF/DOCX), проекту и типу. По умолчанию результаты только из актуальных версий.
10. **Мобильный режим:** нижняя навигация (Проекты · Поиск · + · Задачи · Профиль). Большая кнопка «+» открывает «Фото с объекта / Голосовая заметка / Загрузить файл». Карточка документа на телефоне — превью на весь экран и свайп между ревизиями.

## 4. Telegram-бот против веб-приложения (PWA)

| Критерий | Telegram-бот / Mini App | Веб-приложение (PWA) |
|---|---|---|
| Порог входа | Нулевой: команда уже живёт в Telegram | Нужно открыть ссылку и «добавить на экран» |
| Быстрый ввод (фото, голос, пересылка переписки) | **Отлично:** переслал сообщение или фото боту, и оно попало в проект | Средне: камера и микрофон доступны, но привычка другая |
| Реестр, таблицы, сравнение версий, просмотр чертежей | Плохо: маленький экран внутри мессенджера, ограниченный UI | **Отлично**, особенно на ПК |
| Файлы | Bot API: загрузка от бота до 50 МБ, скачивание через getFile ~20 МБ (снимается своим Bot API сервером до 2 ГБ) | Без ограничений мессенджера |
| Хранение данных | Mini App сама ничего не хранит, нужен свой бэкенд | Свой бэкенд в любом случае |
| Платформенный риск | **Высокий:** в 2026 г. РКН официально подтвердил замедление Telegram в РФ, звучат прогнозы блокировки. Альтернатива MAX требует юрлица и модерации для Mini Apps | Низкий: работает в любом браузере, включая российский хостинг |
| Подходит для | Сбора входящих: фото, голосовые, «найди крайнюю смету», уведомления «ждём ответа» | Работы с документами, согласований, презентации заказчику |

Источники: [vc.ru: кому не подходят Mini Apps](https://vc.ru/services/1949045-telegram-mini-apps-dlya-kogo-podhodyat-i-komu-ne-stoit-ikh-ispolzovat), [Habr: What is a Telegram Mini App](https://habr.com/en/articles/990338/), [merge.rocks: Mini App vs PWA](https://merge.rocks/blog/how-to-build-a-telegram-mini-app-your-telegram-mini-apps-guide), [fast.io: лимиты файлов Telegram](https://fast.io/resources/telegram-file-size-limit.md), [Habr Q&A: лимит 50 МБ](https://qna.habr.com/q/1223614), [Битрикс24 Журнал: блокировка Telegram 2026](https://www.bitrix24.ru/journal/blokirovka-telegram/), [Коммерсантъ](https://kommersant.ru/doc/8499984), [Sostav: MAX, VK, Telegram](https://www.sostav.ru/blogs/281129/78064)

**Рекомендация: оба, но с ясным разделением ролей.**
- **Веб-приложение (PWA) — основное хранилище и рабочее место:** реестр, версии, согласования, сравнение, сборка документов ИИ-агентом.
- **Telegram-бот — тонкий «вход и пульт»:** переслать фото или документ в нужный проект, задать голосовой вопрос («крайняя смета по Петровскому»), получить ссылку на актуальную версию и уведомления.
- Бот не хранит ничего своего, всё уходит в бэкенд PWA. Если Telegram заблокируют, теряется только канал ввода, а не данные. Логику бота стоит делать переносимой (адаптер), чтобы при необходимости подключить MAX или почту.

## 5. ИИ-агенты для документов (2025–2026)

### Как устроена «сборка документа по шаблону с вопросами»
1. **Шаблоны в DOCX с переменными Jinja2 (docxtpl):** `{{ заказчик.фио }}`, циклы `{%tr for p in позиции %}` для строк таблиц сметы. Важно: тег Jinja должен целиком лежать в одном run Word. [docxtpl/django-docxtpl](https://pypi.org/project/django-docxtpl/), [Softkraft: Python Word automation](https://www.softkraft.co/python-word-automation/)
2. **Схема переменных:** у docxtpl есть получение незаполненных (undeclared) переменных шаблона. Это готовый список того, что агент должен найти или спросить.
3. **Цикл агента:**
   1. Выбор шаблона (договор, приложение, ТЗ, пояснительная записка, акт).
   2. Извлечение данных из **актуальных** версий документов проекта: реквизиты из договора, позиции из сметы, размеры и материалы из спецификации Базиса, требования из ТЗ.
   3. Для каждого поля фиксируется **источник** (документ, ревизия, страница).
   4. Чего не хватает или где есть противоречие, агент спрашивает человека: «В смете rev.4 шпон американский орех, в ТЗ дизайнера — европейский. Какой берём?»
   5. Предпросмотр, правки, утверждение человеком.
   6. Рендер DOCX/PDF, документ сохраняется как новая ревизия со статусом «Черновик».
4. **Claude Agent Skills:** готовые навыки docx/xlsx/pdf. В папку навыка можно положить шаблоны (`assets/`) и скрипты проверки (`scripts/validate.py`), а в контекст модели попадает только результат проверки. [Anthropic: Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills)

### Проверки (guardrails), которые ставят
- **Детерминированные:** схема (JSON Schema или Pydantic) на все поля, типы, форматы (ИНН, БИК, даты, телефоны), диапазоны. Арифметика сметы (сумма строк = итог, НДС) пересчитывается кодом, а не моделью. [Openlayer: hallucination detection 2026](https://www.openlayer.com/blog/stop-llm-hallucinations.md), [Leanware: LLM guardrails](https://www.leanware.co/insights/llm-guardrails)
- **Сверка с источником истины:** номер договора, реквизиты и суммы берутся из реестра и карточки проекта, а не генерируются.
- **Только актуальные версии:** агент по умолчанию не видит документы со статусом «Заменён». Если ссылается на старую ревизию, выводит явное предупреждение.
- **Цитирование источников:** к каждому факту в черновике подсвечивается, откуда он взят.
- **Чек-лист по типу документа:** для договора — предмет, сроки, порядок оплаты, приложения, подписи. [Gen AI in legal practice: чек-листы верификации](https://oercollective.caul.edu.au/gen-ai-legal-practice/?p=109)
- **Человек в контуре:** ИИ создаёт только «Черновик». Статусы «Утверждено» и «В производство» ставит человек, и это видно в журнале.

## 6. Рекомендуемая структура проекта для АРХИВУД

**Код проекта:** `АВ-2026-014 Петровский-кухня` (год, порядковый номер, короткое имя).
**Код документа:** `<раздел>-<номер>`, например `КД-03`. Ревизия хранится отдельным полем, а не в имени файла.

| Раздел | Код | Что внутри |
|---|---|---|
| 01 Договор и финансы | ДГ | Договор, допсоглашения, приложения, счета, акты, КП |
| 02 Сметы и расчёты | СМ | Смета, калькуляции, расчёт материалов |
| 03 Исходные данные заказчика | ИД | ТЗ, дизайн-проект, визуализации дизайнера, планы, обмеры, пожелания |
| 04 Замеры | ЗМ | Замер, фото замера, лазерные обмеры |
| 05 Конструкторская документация | КД | Чертежи на согласование, модели Базиса, спецификации |
| 06 Согласования | СГ | Пакеты «на согласование» с ответом заказчика или дизайнера (утверждено / с замечаниями / переделать) |
| 07 В производство | ПР | Утверждённый комплект: рабочие чертежи, карты раскроя, ЧПУ, ведомость закупки (только статус «В производство») |
| 08 Материалы и образцы | МТ | Шпон, эмаль, фурнитура скрытого монтажа (паспорта, образцы, фото выкрасов) |
| 09 Объект и монтаж | ОБ | Фото с объекта, акты скрытых работ, замечания, финальные фото |
| 10 Переписка и решения | ПП | Важные сообщения из Telegram и почты, протоколы встреч, вопросы и ответы (RFI) |
| 11 Пояснительные записки и прочее | ПЗ | Пояснительные записки, гарантия, инструкции по уходу |

**Статусы документа:** Черновик → На согласовании → Утверждено (с замечаниями) → В производство → Заменён / Аннулирован.
**Ревизии:** `P01, P02…` для вариантов до утверждения, `C01, C02…` для утверждённых. Новая утверждённая ревизия автоматически переводит предыдущую в «Заменён».

**Этапы проекта (канбан):** Заявка → Замер → КП/Смета → Договор → Конструкторская разработка → Согласование чертежей → Производство → Монтаж → Сдача → Гарантия.
